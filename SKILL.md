# pod2-config — POD 2.0 configuration JSON

POD 2.0 stores each POD as JSON: `pages[]` and `dialogs[]` of widget nodes `{id, widget, properties, events, aggregations, layoutData}`; `events.<name>` is an ordered array of `{id, action, properties}`; property values bind to the POD context (`{/workList/lastSelected/sfc}`, `{= %{/workList/selected/length} === 1 }`, `{i18n>key}`). The designer copies/pastes pages, dialogs and plugins as exactly this JSON.

## Workflow

1. **Deliverable is always the complete POD export** (the user can only Import whole PODs, not single pages/plugins). Existing POD → ask for the export (or find it in the repo), patch it programmatically (node one-liner: locate node by id, splice/replace, add page `events`), write it as a **new file** next to the original (`<POD_ID>.<feature>.json`), never overwrite the original. New POD → copy the closest template and fill it. A fragment file (node subtree, `pageEnter` block) may be produced *in addition* for review/diffing, but the full export is what you hand over.
2. **Pick the base.** New POD → copy the closest template from `templates/` (`WORK_CENTER` = SFC@work center, `OPERATION_ACTIVITY` = SFC@operation with DynamicPage header, `ORDER` = process/production order with phases). Existing POD → ask for the export or the copied page/dialog JSON; never guess the current structure.
3. **Print a 5-line plan** before JSON: target page + aggregation path · new widgets (class, id) · actions in order · bindings/variables used · placeholders the user must resolve. Ask only if the target page or a binding source is genuinely ambiguous.
4. **Emit JSON** following the hard rules below. Prefer copying a proven snippet from `references/patterns.md` or a template over composing from scratch.
5. **Validate**: `node ~/.claude/skills/pod2-config/scripts/validate-pod.js <file> [--i18n references/i18n-keys.txt]`. Fix errors; report warnings that matter (unknown namespace, placeholder left, dangling dialog/page reference).
6. **Hand-over**: name the full export file to Import (Manage PODs 2.0 → Import) and which placeholders to fix in the designer (Production Process browse dialog rewrites id/key/endpoint). Remind: Save, then Run. Only mention clipboard paste as an optional alternative.

**Dashboards / show PP outputs or context values (fast path):** a request like "build a dashboard in tab X from PP Y with outputs A, B, C" is a spec, not hand-written JSON. (1) Ask only what can't be defaulted: value scale of numeric PP outputs (percent 0–100 vs fraction 0–1) and PP input parameters; layout defaults to context strip + tiles, hero = the headline KPI. (2) Write `<POD_ID>.<prefix>.spec.json` next to the export (format: patterns.md §18). (3) `node ~/.claude/skills/pod2-config/scripts/build-panel.js <export.json> <spec.json> --preview` → writes `<POD_ID>.<prefix>.json` (+ `.preview.html`), validates against the baseline, refuses to overwrite the input. Re-running with the same prefix replaces the panel. A mockup request before building = run the same command and open the preview (or sketch inline if the user wants it instantly). Hand-over as in step 6.

**Preview (on request only — "preview the POD" / "show me the layout" / "Fiori preview"):** `node ~/.claude/skills/pod2-config/scripts/preview-pod.js <export.json>` → writes `<export>.preview.html`, one self-contained file that boots SAPUI5 (`sap_horizon`) from the public CDN and instantiates the real controls from the config against a mock POD-context model, so bindings/`{= …}` expressions resolve. Pages render as tabs, dialogs as buttons that open them; custom `sap.dm.dme.pod2.*` widgets show as labelled placeholders (not on the CDN). PP `outputVariable`s get sample values from their `responseDataType` (tab/page enter events don't run), POD style props (`backgroundColor`, `fontColor`, padding, gap) are applied as CSS, `{i18n>key}` shows as a humanised key. Open in a browser (needs internet); a sandboxed pane may need it served over `http://127.0.0.1` (`python3 -m http.server`). Preview only — never imported, not part of the deliverable.

## Hard rules

- Widget `id`s unique per page/dialog. When copying a subtree elsewhere, re-id every widget node (`NavigateToWidget` resolves globally; collisions misroute silently). Action `id`s may repeat.
- Use only widget/action classes listed in `references/widgets.md` / `actions.md` (verified from exports) or marked *likely*; for anything marked *unverified*, tell the user to configure it once in the designer, copy it, and paste the JSON back. Never invent class names or property keys.
- Children only under `aggregations.<name>` using a name from the container→aggregation map in `references/json-grammar.md` (same set as the validator's `AGG`); never invent aggregation names.
- Keep the page style you are editing (Toolbar header vs DynamicPage). Preserve existing `customHeader`/`headerActions`/`headerContent`; new top-level pages copy the template header (back button, title, spacer, Clock, MessageHistory, NotificationStateIcon).
- Action chains: `Confirm` first (cancel skips the rest), `BusyIndicator` before long calls, `CloseDialog` last; a failing action stops the chain. Data Collection save = `LogDataCollectionGroup → RefreshDataCollectionGroups → CloseDialog`.
- Production Process: never invent ids/keys — use `REPLACE_WITH_PP_ID_<NAME>` / `REG_REPLACE_WITH_PP_KEY_<NAME>` / `REPLACE_WITH_TENANT`; map inputs with `{/binding}` or `valueType:"variable"`; set `outputVariable` when the output is displayed; output only available when the PP call is synchronous.
- Single-selection actions get `enabled: "{= %{/workList/selected/length} === 1 }"`. Show/hide with `visible`/`enabled` expressions on context paths (see binding-and-context.md); truthiness of optional variables via `!!%{...}`. Any string/enum prop may be an expression: colour by value (`color: "{= %{/x} < 50 ? '#BB0000' : '#2B7D2B' }"`), button style (`type`), `icon`, `text`. Write a POD variable from a button with `model.SetProperty {path,value}`; load data on page open via the page node's `events.pageEnter`.
- Colours: `sap.m.Text`/`Label` take `fontColor` (a `color` key is silently ignored — no error, just no colour); `sap.ui.core.Icon` takes `color`; HBox/VBox/Button/Toolbar take `backgroundColor`. Expression-bound `backgroundColor`/`fontColor` work at runtime (verified 2026-09). A palette written by `pageEnter` → `SetProperty` is **not** guaranteed to run before first render — every palette-driven expression must embed its default: `{= ${/my/colors/bg} || '#FFFFFF' }` (see patterns.md §16).
- Labels: `{i18n>key}` only for keys in `references/i18n-keys.txt`; custom text is a literal string (not translated). Custom dialog inputs bind their value to a custom path under one root (`/myDialog/input/field`).
- Full export carries `_version: 1`, `contentDensity: "Compact"`, `target: "CLOUD"`, `createdFromTemplate`; keep whatever top-level keys the user's export already has (don't add `target` if it is absent — it imported fine without). Fragments (review only) omit all top-level keys.
- **Naming new ids:** follow the scheme of the siblings/section you insert into — read the parent's children first. Pattern `<Section>_<Subject><Role>`, PascalCase, English subject even when the visible label is German; Role = what the node is (`Box`, `Label`, `Value`, `Title`, `Button`, `Dialog`, `Table`…). E.g. next to `ResourceCard_ReasonCodeBox/Label/Value` a new field is `ResourceCard_CreatedByBox/Label/Value`, a heading `ResourceCard_LastDowntimeTitle`. No tool/agent prefixes (`OD_`, `My`, `New`, `Custom`), no doubled roles (`…BoxLabel`), no numbered ids (`Text12`). No convention in that area → derive `<Section>` from the page/dialog id. Grep the whole export before writing: every new widget id must be unique.
- Tenant exports re-number only designer-generated ids (`HBox243`, `Text167`) on re-import; explicit ids like the above survive. Patch scripts locate nodes by those explicit ids or a stable binding expression, never by a numbered id from an older export.
- Validate against the export's **baseline**, not zero: run the validator on the untouched export first; tenant exports carry pre-existing errors (custom widget columns without `field`, `NavigateToPage` to removed pages). Deliver when the error count is unchanged and new warnings are explained (custom actions/bundles warn by design).
- Custom plugin bundles are usable in config as `{i18n<Component>>key}` (e.g. `{i18nEquipmentOverview>col.order}`); keys come from the plugin's `i18n/i18n.properties`, the validator flags them as unknown — expected.
- Lists: no templating exists. N fixed slots bound to `/<list>/<i>/…` + `/<list>/length` (patterns.md §17); the source widget's `max*` props must not exceed the slot count.
- Tenant data (hosts, PP ids, user ids) never goes into reusable snippets; sanitize anything you echo back from a customer export.

## References (read what the task needs)

- `references/json-grammar.md` — export shape, node shape, container→aggregation map, page/dialog nodes, columns, fragments.
- `references/binding-and-context.md` — binding forms, expression cheat sheet, roots per template, PP input mapping, i18n bundles/keys, URL parameters.
- `references/pod-context.md` — full runtime context schema (what every `{/…}` can point to).
- `references/widgets.md` — standard widget classes, JSON property keys, events, table `columns[].field` values.
- `references/actions.md` — action classes, properties, chain semantics, Production Process shape.
- `references/patterns.md` — 18 recipes (dialog→PP→output, dynamic visibility, exec toolbar, new tab, Confirm+Busy+PP, OpenURL, header field, back button, new page, menu, DC save chain, SVG lamp, KPI tile w/ threshold colour, pageEnter data load, SetProperty sidebar selector, status card, fixed-slot list + "+N" overflow, §18 spec format for build-panel.js).
- `references/sap-catalog.md` — all 147 SAP plugins/actions with IDs and help slugs; `references/sources.md` — URLs + re-harvest recipe.
- `scripts/build-panel.js` — spec → dashboard panel generator (tab/page/dialog/node target, PP load chain, threshold tiles; `--self-test`). `scripts/preview-pod.js` — on-request Fiori preview generator (self-contained HTML, real UI5 from CDN, mock context model; `--self-test`). `scripts/validate-pod.js` — structural validator.
- `templates/*.json` — SAP-generated WORK_CENTER / OPERATION_ACTIVITY / ORDER exports (tenant-neutral). `templates/PALETTE.json` is a fixture, not a starting point: every designer palette widget dropped once (BLANK), i.e. ground truth for class names and designer-default properties.

Out of scope: writing custom plugins (use `pod-plugin`), local harness (`pod-plugin-localhost`), production process design, tenant calls.

## Keep this skill current
At the end of any session that patched a POD config: add new verified facts (widget props, binding forms, designer behaviour, validator quirks) to the matching reference file and a recipe to `patterns.md` if reusable. Same rule for `pod-plugin` when plugin knowledge is gained.
